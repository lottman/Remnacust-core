# Remnacust Core

Форк Xray-core для Remnacust. Обслуживает клиентские соединения, выполняет маршрутизацию и применяет политики хостов, тегов и устройств. Здесь также находятся исходники редактора и браузерной проверки конфигураций.

Версия **1.1.10** на основе опубликованного официального тега **Xray v26.10.10**, коммит `701af60772cda123492f86e383e1fdba066614a9`. Авторы Xray пометили этот релиз как prerelease. Коммиты из `main` после тега исключены; политика дальнейших обновлений — только опубликованные официальные релизы. Наши XERA, политики устройств/хостов, квоты и применение поколений остаются расширениями форка. [Совместимость](docs/COMPATIBILITY.md). WASM, схемы и архив ноды синхронизированы с ядром 1.1.10 для выпуска 1.2.73.

**Версия 1.1.10** · **Основа: Xray-core v26.10.10** · [Панель](https://github.com/lottman/Remnacust-panel) · [Нода](https://github.com/lottman/Remnacust-node)

Имя Go-модуля `github.com/xtls/xray-core` сохранено для совместимости импортов. Исходники зависимости olcRTC находятся в `vendor/olcrtc`; отдельная загрузка из файлового менеджера не нужна.

## Сборка

Нужен Go 1.27.

```bash
git clone https://github.com/lottman/Remnacust-core.git
cd Remnacust-core/xray
mkdir -p bin
CGO_ENABLED=0 go build -trimpath \
  -ldflags '-s -w -X github.com/xtls/xray-core/core.build=Remnacust-1.1.10' \
  -o bin/xray ./main
./bin/xray version
```

В Windows задайте `$env:CGO_ENABLED='0'` и укажите `bin/xray.exe`. При установке ноды [установщик](https://github.com/lottman/Remnacust-installer) скачивает готовый Docker-образ с агентом и ядром; сборки на сервере нет.

Для отдельного обновления ядра из панели доступны [проверенные бинарники 1.1.10](https://github.com/lottman/Remnacust-core/releases/tag/v1.1.10) для Linux amd64 и arm64 с SHA256SUMS. Workflow `Publish verified core binaries` собирает существующий тег на нативных runner, проверяет версию и конфигурацию и создаёт черновик. После проверки и публикации обновите каталог панели через `panel/backend/scripts/sync-core-catalog.py` с тем же тегом и полным коммитом исходников. Опубликованные файлы не заменяются.

## Проверка и запуск

```bash
./bin/xray run -test -config /path/to/config.json
./bin/xray run -config /path/to/config.json
```

Первая команда проверяет конфигурацию и завершает работу. Она не проверяет внешнюю доступность портов, DNS и сертификатов. Если ядром управляет агент, меняйте рабочий профиль в панели: агент формирует runtime-конфигурацию.

Для расширенных квот, скорости и устройств нужны совместимые версии панели, агента и ядра. Замена только бинарного файла не обновляет агент.

## Редактор панели

Клонируйте `Remnacust-panel` рядом с этим репозиторием. Из корня `Remnacust-core`:

Команда обновит схему, `main.wasm` и `wasm_exec.js` в соседней панели. Для другого расположения задайте `REMNACUST_PANEL_SOURCE=/path/to/Remnacust-panel`. Затем пересоберите образ панели. [Исходники редактора](editor/README.md).

## Xera HTTP

Xera HTTP — форк транспорта XHTTP (SplitHTTP) из Xray-core, с собственными настройками `network: "xera-http"` и `xeraHttpSettings`. Для соединения его должны поддерживать ядра обеих сторон. Настройка, отличия, режимы и переход с XHTTP описаны в [руководстве панели](https://github.com/lottman/Remnacust-panel/blob/main/panel/frontend/public/documentation/guide-ru.md#транспорт-xera-http).

## Лицензии

Ядро сохраняет [MPL-2.0](xray/LICENSE) и авторство Xray-core. Редактор и зависимости сохраняют собственные лицензии. Подробности: [NOTICE.md](NOTICE.md).

В 1.1.5 обновлены Go и HTTP/2-зависимость с исправлениями уязвимостей; проверки гонок и `govulncheck` выполняются в CI. Отзыв устройства по-прежнему закрывает уже открытый поток, включая передачу, обходящую внутренние буферы. Соединения выбираются по авторизованному идентификатору, а не по IP: другие устройства за тем же NAT остаются подключёнными. Повторное разрешение устройства снимает запрет новых подключений. Этот сценарий проверяется настоящими VLESS-соединениями в CI.

## Квитанции расхода: неопубликованный код

Приватный Stats API получил `remnacust-usage-receipts-v1/Exchange` и `api usage-receipt`. В Node runtime счётчики сначала сохраняются в приватный ограниченный журнал, затем вычитаются из RAM. Повторы возвращают тот же снимок до ACK после SQL-коммита. Номер, процесс и int64 передаются строками; старые destructive вызовы не обходят активный поток. Есть race-тесты настоящего перезапуска и CLI по Unix-сокету. Обычный клиентский протокол не меняется.

Это часть ещё незавершённой автономности: успешная квитанция не доказывает готовность глобального пользовательского бюджета и автоматической первой выдачи. Node Docker собирает ядро из закреплённого source archive; перед выпуском архив и версии нужно обновить. Эти изменения ещё не опубликованы.

## Расход вне гранта: неопубликованный код

Добавлен приватный контракт `remnacust-unreserved-usage-v1`: исходные сырые байты привязаны к конкретному банку/эпохе, владельцу и коэффициенту. Конечные гранты не считаются повторно; recovery-исключения сохраняют gross-учёт. Счётчики входят в durable-квитанции и защищены от отдельного legacy reset. Проверены Linux `-race`, восстановление журнала и смена коэффициента/счёта. В панели подключён рендерер счетов с commit-before-delivery привязкой цены/экземпляра; нода и установщик блокируют downgrade без нового учёта. Координатор и готовые образы выпущены в 1.2.59. Полный установленный E2E всех операций не подтверждён; ограничения перечислены в описании выпуска. Подробности — [LIVE-PORTS-DESIGN.md](https://github.com/lottman/Remnacust-panel/blob/main/docs/LIVE-PORTS-DESIGN.md), глава о расходе вне локального гранта.


В неопубликованном коде исправлен recovery-барьер: исключение из USER-гранта сохраняется, но временная сверка расхода ожидает допущенные recovery-буферы до ACK. Проверены отмена ожидания, другие владельцы, сохранность HOST-гранта и метаданные расхода при заблокированном quota-журнале (Linux -race). Снимки подготовленной/подтверждённой политики панели ещё предстоит связать с полным автоматическим перераспределением.

## Области ограничения скорости

Политика ограничивает все соединения и устройства одного владельца в области хоста; загрузка и отдача используют общий бюджет. Скорость пользователя тега применяется отдельно на каждом участвующем хосте, общая скорость — отдельный пул. Панель задаёт скорость в Mbps, а политика ядра — в байтах в секунду. [Настройка и примеры](https://github.com/lottman/Remnacust-panel/blob/main/docs/HOST-LIMITS.md).

Совместимое применение конфигурации через runtime API сохраняет существующие соединения. Смена порта, транспорта или несовместимых настроек работающего listener отклоняется; для неё нужен отдельный listener либо явное обслуживание. Обновление бинарника ядра — отдельная операция с возможным разрывом соединений. Техническая ошибка не подменяется автоматическим перезапуском. [Сверка документации компонентов](https://github.com/lottman/Remnacust-panel/blob/main/docs/DOCUMENTATION-SYNC.md).

## Динамическая скорость устройств (1.1.10)

В host-policy-v2 добавлено `deviceBytesPerSecond` на группу и признак `remnacust-device-speed-v1`. Предел устройства суммирует все соединения и оба направления его аутентифицированного ключа. Очередь скорости делит общий бюджет сначала между пользователями, затем между активными ключами каждого пользователя. Количество потоков не умножает долю; неактивные ключи не резервируют скорость. При свободном канале активное устройство использует доступную часть общего предела, но не превышает собственный. Это ограничение скорости, а не гарантированная пропускная способность физического канала. Без заданного общего предела ядро не определяет его ёмкость автоматически.

Очередь ограничена по числу ожидающих запросов; отменённые запросы удаляются. Существующие квоты, отзыв ключей и повторная проверка политики после ожидания сохраняются. Тесты очереди и диспетчера запускаются через `go test -race ./app/dispatcher`. Клиентские протоколы и формат выданных ключей не изменены.
