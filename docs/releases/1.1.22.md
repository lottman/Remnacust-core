# Remnacust Core 1.1.22

Добавлена необязательная адаптация Xera HTTP с тремя профилями измеренной обратной связи: «Сбалансированный» (balanced), «Низкая задержка» (low-latency) и «Нестабильная сеть» (unstable-network). Используются реальные HTTP-ответы, ход передачи и ожидание запросов. Профили отличаются реакцией на перегрузку; это не обучение ИИ и не новые протоколы передачи.

В `streamSettings.xeraHttpSettings.adaptive` обязательны все три поля: `mode`, `minStreams` и `maxStreams`. Целые границы — от 1 до 32, минимум не больше максимума. Форма панели предлагает 4/32; начальный предел 8 ограничивается выбранным диапазоном. Минимум не создаёт запросов при отсутствии трафика.

Границы относятся к одновременно активным HTTP-запросам отдельно для каждого направления, назначения и версии настроек транспорта. Они не задают число физических TCP-соединений, пользователей, всех сессий устройства или загрузку CPU. Подстройка влияет на допуск новых запросов; начатые запросы не прерываются и не отправляются повторно.

Без adaptive сохраняется прежнее поведение. Ручной JSON и extra, режимы передачи auto/stream-auto, ALPN, padding и квоты сохраняются. Форма панели меняет JSON-черновик только по явному действию «Применить в JSON»; затем нужно сохранить профиль и обновить подписку клиента. Для работы адаптации требуется Core 1.1.22 или новее у клиента с поддержкой Xera HTTP. Обновление панели или Node не обновляет ядро приложения.

Существующий формат обмена Xera сохраняется. Нативная проверка Core 1.1.22↔1.1.21 в Linux завершилась успешно: 82 сценария IPv4/IPv6, TLS HTTP/1.1, HTTP/2, HTTP/3 и REALITY, четыре прежних режима и три профиля адаптации. Проверки реального Chrome с IPv6 под детектором гонок и трёхкратный набор XDRIVE в Windows также прошли. Адаптация не гарантирует невидимость для DPI, доступность заблокированного адреса или преимущество в сетях России и Китая. [Настройки и ограничения](../XERA-HTTP.md#адаптивное-управление-http-запросами).

Приватные операции управления учитывают отмену RPC, включая прежние gRPC-операции пользователей и сброса статистики. Запрос, отменённый во время ожидания, не начинает отложенное изменение после освобождения Core. Отмена ограничивает дальнейшую работу, но сама по себе не откатывает уже применённые изменения. Для согласованного управления используйте Node 1.1.37 с дедлайнами и защитой от пересечения изменений конфигурации, пользователей и сброса статистики.

XDRIVE ограничивает число ожидающих сегментов WAL. При заполнении окна отправитель ожидает продвижения получателя; отсутствие прогресса в течение TTL сессии завершает передачу ошибкой. Данные закрытых сеансов очищаются с ограничением объёма работы и повтором после ошибок хранилища. Исправления WAL и отмены gRPC сохраняют прежние форматы обмена и конфигурации; новых параметров для них нет.

Обновлены зависимости редактора, включая DOMPurify 3.4.18. Официальная основа остаётся Xray v26.11.9. Комплект: Core 1.1.22, Node 1.1.37, Panel/Page 1.1.7.126, Installer 1.2.174. Установленные ноды и приложения пользователей обновляются отдельно; проверяйте фактически запущенное ядро.

## English

Adds optional Xera HTTP adaptation with three measured-feedback profiles: Balanced (balanced), Low latency (low-latency) and Unstable network (unstable-network). They use real HTTP responses, transfer progress and request waiting. The profiles differ in their congestion response; they are neither AI training nor new transfer protocols.

All three fields in `streamSettings.xeraHttpSettings.adaptive` are required: `mode`, `minStreams` and `maxStreams`. Bounds must be integers from 1 to 32, with the minimum no greater than the maximum. The panel form offers 4/32; the initial limit of 8 is clamped into the selected range. The minimum creates no requests while idle.

Bounds apply to simultaneously active HTTP requests separately for each direction, destination and generation of transport settings. They do not specify physical TCP connection counts, users, all device sessions or CPU load. Adjustment affects admission of new requests; requests already started are neither aborted nor replayed.

Without adaptive, previous behavior is preserved. Manual JSON and extra, auto/stream-auto transfer modes, ALPN, padding and quotas remain intact. The panel form changes the JSON draft only through an explicit Apply to JSON action; save the profile and refresh the client subscription afterwards. Adaptation needs Core 1.1.22 or later in a client supporting Xera HTTP. Updating Panel or Node does not update the application core.

The existing Xera wire format is retained. Native Linux interoperability between Core 1.1.22 and 1.1.21 passed 82 IPv4/IPv6 scenarios covering TLS HTTP/1.1, HTTP/2, HTTP/3 and REALITY, four existing modes and three adaptation profiles. Real Chrome with IPv6 under the race detector and three repetitions of the Windows XDRIVE suite also passed. Adaptation cannot guarantee DPI invisibility, reachability of a blocked address or an advantage on networks in Russia or China. [Settings and limits](../XERA-HTTP.md#adaptive-http-request-control).

Private management operations honor RPC cancellation, including legacy gRPC user mutations and statistics resets. A request canceled while waiting cannot begin its deferred mutation after Core becomes available. Cancellation limits further work but does not itself roll back changes already applied. Use Node 1.1.37 for coordinated management with deadlines and protection against overlapping configuration changes, user mutations and statistics resets.

XDRIVE bounds pending WAL segments. When the window fills, the sender waits for receiver progress; no progress within the session TTL ends the transfer with an error. Closed-session data cleanup is bounded and retried after storage errors. The WAL and gRPC cancellation fixes retain existing wire and configuration formats and add no settings.

Updates editor dependencies, including DOMPurify 3.4.18. The official baseline remains Xray v26.11.9. Bundle: Core 1.1.22, Node 1.1.37, Panel/Page 1.1.7.126 and Installer 1.2.174. Installed nodes and user applications require separate updates; verify the core actually running.
